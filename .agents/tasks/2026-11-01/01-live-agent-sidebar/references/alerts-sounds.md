## Contract and acceptance detail

- The provider adapter must supply namespaced provider/account/agent identity, an invocation or run generation, a monotonic event sequence or unique event ID, and a reconnect cursor. Bind a sound dedupe key to that identity plus run generation and event ID. Do not key by title, workspace path, row position, or terminal text.
- Normalize only explicit provider lifecycle evidence. `working`, `waiting`, `idle`, initial snapshot reconciliation, `unknown`, `disconnected`, transport recovery, and repeated/replayed event IDs are silent. A newly admitted `needs_user`/`blocked` event plays the selected attention sound once; a newly admitted `completed` event plays the selected completion sound once. Provider-specific failure mapping must be explicit; unsupported meanings remain Unknown and silent.
- On reconnect, apply the provider's current snapshot without sound, then accept only unseen events after the last acknowledged cursor. If a provider cannot guarantee sequence/replay semantics, reconcile its status without historical sound and report the evidence limit. A new run generation permits a new attention/completion event; stale generations cannot change the row or play sound.
- Persist the master **Play sounds** switch and the selected attention/completion sounds in Zmux-owned preferences. Provide preview buttons that play only the selected sound and do not emit a lifecycle event or system notification. If custom MP3 files are supported, validate the local file and format, explain fallback behavior, and never write provider configuration as a side effect of preview or alert playback.
- With audio enabled, the selected attention/completion sound is emitted once for a new event in foreground and background. With audio disabled, the in-app inbox item and eligible visual system notification remain, but agent-event audio is suppressed. Use one sound path per event so a custom sound and the OS default do not both play. OS permission denial or user-level sound muting is surfaced as unavailable; source scheduling cannot promise audible output.
- Apply the same preference and dedupe behavior to local and authenticated remote provider events. Play remote event sound on the local Mac only. On remote transport loss, invalidate stale state and remain Unknown/Disconnected until current provider evidence returns; reconnect must not replay old sounds. Existing Claude OSC notices can coexist as terminal notices, but must not be mistaken for provider lifecycle or duplicate a correlated provider event.

## Evidence limits

The screenshot is a visual reference only. Existing Rust, terminal-parser, and Swift tests can prove normalization, ownership, replay, dedupe, preference persistence, and bridge scheduling when added, but fixtures do not prove a real provider's lifecycle semantics, remote authentication, macOS audio audibility, or that a user saw an OS banner. Packaged native acceptance must exercise local and authenticated remote provider sessions on macOS with both audio settings and OS notification permissions recorded. Distinguish “scheduled” from user-visible or audible success in the task evidence.
