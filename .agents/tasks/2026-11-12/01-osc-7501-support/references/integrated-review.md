2. **P2, confirmed source defect: explicit close cannot clear records in the Ghostty Session path.** The Session worker aborts the engine before returning `Closed` on the normal Kill shutdown path ([session-runtime/src/lib.rs:1254](/data/PROJECTS/ashutoshpw/zmux/crates/session-runtime/src/lib.rs:1254)). Finalization then calls `terminal_closed()` ([session-runtime/src/lib.rs:1176](/data/PROJECTS/ashutoshpw/zmux/crates/session-runtime/src/lib.rs:1176)). `Engine::abort()` propagates to Ghostty and marks its owner failed ([terminal-adapter/src/engine.rs:490](/data/PROJECTS/ashutoshpw/zmux/crates/terminal-adapter/src/engine.rs:490)); Ghostty's close snapshot rejects a failed owner ([ghostty-vt/src/owner.rs:477](/data/PROJECTS/ashutoshpw/zmux/crates/ghostty-vt/src/owner.rs:477)). Final publication consequently falls back to `State::Failed` with the last published viewport, retaining the old program records. Trigger: a Ghostty-backed Session reports `working`, then receives `request_close`/Kill shutdown. The existing close test uses `Session::spawn` (vt100), and the adapter linked test closes an un-aborted Engine directly, so neither exercises this interleaving.

3. **P2, confirmed source defect: provider alert admission can use the prior command's OSC source lock.** `Runtime::observe` clears a source lock only when it consumes the prompt transition ([desktop-runtime/src/program_status.rs:467](/data/PROJECTS/ashutoshpw/zmux/crates/desktop-runtime/src/program_status.rs:467)). Before that observation, `provider_alert_allowed` finds a track by terminal target alone and uses its existing source without comparing current session/command epochs ([desktop-runtime/src/program_status.rs:550](/data/PROJECTS/ashutoshpw/zmux/crates/desktop-runtime/src/program_status.rs:550)). Remote provider events are admitted before the next `publish` observes the terminal status ([desktop-runtime/src/lib.rs:2243](/data/PROJECTS/ashutoshpw/zmux/crates/desktop-runtime/src/lib.rs:2243)); a rejected event is then permanently suppressed ([desktop-runtime/src/lib.rs:3446](/data/PROJECTS/ashutoshpw/zmux/crates/desktop-runtime/src/lib.rs:3446)). Concrete interleaving: command A wins OSC alert ownership; the PTY parses OSC 133 A for command B; before desktop publication, B's provider emits an alert. The old OSC lock suppresses B's provider event, and the later prompt observation cannot restore it. The pre-spawn route path has the related epoch race: registration reads `Session::snapshot()` at [desktop-runtime/src/lib.rs:3335](/data/PROJECTS/ashutoshpw/zmux/crates/desktop-runtime/src/lib.rs:3335), via a helper that returns the Session's latest published snapshot ([desktop-runtime/src/lib.rs:3528](/data/PROJECTS/ashutoshpw/zmux/crates/desktop-runtime/src/lib.rs:3528)), not a synchronous read of the worker's staged/current command epoch. If the prompt boundary has not reached that snapshot, the route binds to the prior epoch and is pruned when the prompt transition is later consumed ([desktop-runtime/src/program_status.rs:472](/data/PROJECTS/ashutoshpw/zmux/crates/desktop-runtime/src/program_status.rs:472)).

4. **P2, accepted coverage gap, not a confirmed runtime defect: the linked Ghostty Session owner has no Program Status real-PTY round trip.** The query, ordered DA reply, final-drain and lifetime Session fixture at [session-runtime/tests/program_status.rs:76](/data/PROJECTS/ashutoshpw/zmux/crates/session-runtime/tests/program_status.rs:76) uses `Session::spawn` and therefore vt100. The feature-gated Session engine tests in `session-runtime/tests/engine.rs` do not send OSC 7501. These owners do not jointly prove that Session's real PTY writer, final drain, and close path carry the linked engine's Program Status effects. Minimal follow-up: reuse the existing `Fixture` and real-PTY query/final-drain scenario under `#[cfg(feature = "ghostty")]` with `Session::spawn_with_engine`; assert `FEATURE_DETECTION_REPLY` followed by Ghostty's primary DA bytes `ESC [ ? 62 ; 22 c`, then assert final-drain retirement/retention and explicit-close clearing. Share the scenario with the default-engine case instead of duplicating the protocol matrix.

5. **P3, protocol edge defect: an over-limit malformed duplicate `id` rejects the entire report instead of being skipped.** `parse_pairs` checks ID byte/segment/depth limits before checking `valid_value` ([program-status/src/lib.rs:752](/data/PROJECTS/ashutoshpw/zmux/crates/program-status/src/lib.rs:752)). For example, `state=working:id=build/test:id=<33-byte segment containing @>` exceeds the segment limit and also contains a forbidden wire byte. The current code returns `IdSegmentTooLong` before reaching the malformed-pair skip, so the otherwise valid update is discarded; the protocol design says malformed pairs are skipped and preserve a preceding valid ID. Existing coverage checks the two cases separately ([program-status/tests/protocol.rs:534](/data/PROJECTS/ashutoshpw/zmux/crates/program-status/tests/protocol.rs:534)).
